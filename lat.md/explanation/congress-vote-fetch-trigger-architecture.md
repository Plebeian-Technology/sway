# Congress vote fetch trigger architecture

Sway relies on scheduled sweeps and direct outbound API queries rather than inbound email alerts to discover and fetch congressional roll-call votes.

## Why email alert ingestion was evaluated and rejected

Congress.gov email notifications through GovDelivery were evaluated as an event-driven trigger for legislator vote fetching and rejected across four operational dimensions.

The proposal sought to connect an inbound mailbox over IMAP to receive Congress.gov alerts, parse bill identifiers, and enqueue [[app/jobs/legislator_vote_fetch_job.rb#LegislatorVoteFetchJob]] faster than the daily sweep. Analysis of the subscription model, operational profile, message format, and actual notification latency proved that inbound email ingestion introduces severe failure modes without delivering any timeliness advantage over Sway's existing outbound architecture.

### Subscription coverage and alert noise

Automated alert management is blocked by bot defenses, while saved searches cannot filter exclusively for roll calls.

Congress.gov requires an interactive user account created through a browser. The alert management interface sits behind Akamai Bot Manager, which rejects automated HTTP requests with `403 Forbidden` and provides no public subscription API in `api.congress.gov`. Consequently, alert subscriptions cannot be provisioned or maintained programmatically.

Per-bill subscriptions demand manual operator intervention for every federal measure, which is unmaintainable. Broad saved-search alerts track entire legislative sessions (such as the 119th Congress) but trigger on every recorded action, including cosponsor changes, committee referrals, bill text versions, amendments, and cost estimates. Because roll-call votes represent less than one percent of all congressional actions, a broad subscription floods the mailbox with thousands of irrelevant emails weekly, wasting worker processing cycles on non-vote traffic.

### Operational burden and security on edge hardware

Running inbound email protocols introduces hung socket risks, unauthenticated spam exposure, and credential maintenance to the worker host.

Sway deploys via Docker to a Raspberry Pi with multi-database SQLite storage and Solid Queue background workers. Inbound email processing over IMAP requires persistent polling connections via `Net::IMAP`. Network stalls or dropped TCP sockets during remote IMAP polling can deadlock worker threads on the constrained host unless wrapped in elaborate timeout handling.

Inbound mailboxes also present an open attack surface. Standard SMTP does not authenticate senders, allowing malicious actors to spoof messages from federal notification domains or flood the address with arbitrary messages. Preventing denial-of-service attacks or falsified fetch triggers would require implementing cryptographic DKIM verification, SPF evaluation, and DMARC enforcement inside the Rails worker pipeline. Furthermore, headless IMAP accounts require ongoing credential rotation, OAuth token refreshes, and mailbox purging protocols to avoid storage exhaustion.

### Template drift and machine readability

GovDelivery email notifications lack machine-readable metadata and wrap URLs in redirects, causing brittle parsing.

Alerts generated by GovDelivery are formatted as visual HTML for human readers. They contain no structured JSON-LD payloads, microdata annotations, or machine headers identifying bill numbers or roll-call indices. Hyperlinks within the emails route through GovDelivery click-tracking redirection domains (`links.govdelivery.com` or `lnks.gd`), obscuring underlying canonical identifiers.

Parsing these messages requires heuristic DOM queries and regular expressions against narrative English action text. Strict parsing rules designed to fail loudly when templates change inevitably trigger Sentry alert storms and queue backlogs whenever GovDelivery alters styling or tracking wrappers. Conversely, permissive parsing risks pairing procedural motions (such as cloture or tabling votes) with legislation, violating the vote-identity invariants detailed in [[roll-call-identity]]. Furthermore, [[app/jobs/legislator_vote_fetch_job.rb#LegislatorVoteFetchJob]] requires existing roll-call numbers and vote dates on the [[app/models/roll_call.rb#RollCall]] record; an email notification stating that an action occurred lacks the necessary roll-call metadata to populate those fields without secondary scraping.

### Timeliness comparison and latency evidence

GovDelivery email batching introduces hours of delivery latency compared to direct chamber feeds, while Congress.gov REST endpoints exhibit publication delays.

The primary rationale for event-driven alerts was reducing vote discovery latency below the 24-hour sweep cycle. However, GovDelivery does not broadcast real-time messages when votes conclude. Instead, notifications are batched into twice-daily dispatches: a morning run around 08:30 Eastern Time and an afternoon run around 14:30 Eastern Time.

Congressional floor votes frequently occur during late afternoon and evening sessions (between 17:00 and 22:00 Eastern Time). Votes cast during evening sessions are held until the morning batch at ~08:30 ET (~12:30 UTC). Sway's daily sweep job ([[app/jobs/legislator_vote_sweep_job.rb#LegislatorVoteSweepJob]]) runs at 09:00 UTC (05:00 Eastern Daylight Time / 04:00 Eastern Standard Time). The morning GovDelivery email alert arrives three and a half hours *after* Sway has already discovered, scraped, verified, and recorded the vote.

Upstream publication schedules vary sharply by chamber and source. The Senate Secretary publishes official roll-call XML feeds on `senate.gov` quickly, typically within 5 to 30 minutes of the gavel falling. Similarly, the House Clerk publishes roll-call XML on `clerk.house.gov` shortly after floor votes. However, empirical data from the 119th Congress proves that the official Congress.gov v3 REST API publishes House roll calls roughly 24 hours after votes occur; for example, roll calls 71, 72, and 74 in the second session recorded `updateDate` values approximately 24 hours after their respective `startDate`.

Because Congress.gov publishes House roll calls on this lagged schedule, [[app/scraper/scraper/congress/house/legislator_votes.rb#LegislatorVotes]] uses a dual-stage pipeline that queries the Congress.gov REST endpoint first and falls back to `clerk.house.gov` XML whenever Stage 1 raises [[app/scraper/scraper/congress/roll_call_unavailable.rb#RollCallUnavailable]] (any non-200 HTTP response, or a 200 body that is blank or does not parse to a Hash containing `houseRollCallVoteMemberVotes`). Even if an inbound email arrived earlier than the daily sweep, the primary Congress.gov API would still fail on newly cast votes, requiring the same Clerk XML fallback that the scheduled sweep utilizes.

### Definitive feasibility decision

The evaluation conclusively rejects inbound email alert ingestion in favor of direct outbound chamber feeds.

The feasibility decision for Congress email alerts is **REJECT**. Inbound email ingestion fails all operational criteria: automated subscription coverage is impossible, maintenance and security overhead on edge hardware is excessive, template drift introduces parser fragility, and batched email delivery offers zero timeliness benefit over outbound polling.

## How roll calls are discovered and paced today

The daily vote sweep polls settled and active bills with roll-call pointers while protecting against cross-year roll call collisions.

Congressional roll calls are managed through a staged outbound pipeline comprising [[app/jobs/legislator_vote_sweep_job.rb#LegislatorVoteSweepJob]], [[app/jobs/legislator_vote_fetch_job.rb#LegislatorVoteFetchJob]], and [[app/services/congress_legislator_vote_update_service.rb#CongressLegislatorVoteUpdateService]]:

1. **Daily scheduled sweep**: [[config/recurring.yml]] schedules [[app/jobs/legislator_vote_sweep_job.rb#LegislatorVoteSweepJob]] at `09:00 UTC` ("0 9 * * *") on the `:background` queue. For jurisdictions configured with `:congress_dot_gov`, the sweep queries all bills with non-null `house_roll_call_vote_number` or `senate_roll_call_vote_number` values on their associated [[app/models/roll_call.rb#RollCall]] record.
2. **Settled bill filtering**: The sweep skips bills whose newest vote occurred in a previous calendar year and which already possess recorded, non-inferred [[app/models/legislator_vote.rb#LegislatorVote]] records. Because congressional roll-call numbering restarts every January (as documented in [[congress-roll-calls]]), re-polling an older bill's roll-call number against the current year would fetch an unrelated modern vote.
3. **Pacing and write protection**: To protect the multi-database SQLite WAL file from write contention and lock timeouts on Raspberry Pi hardware, the sweep spaces enqueued jobs by 0.5 seconds per bill up to an 1800-second (30-minute) ceiling (`wait_seconds = [i * 0.5, WAIT_CEILING_SECONDS].min`).
4. **Concurrency control**: [[app/jobs/legislator_vote_fetch_job.rb#LegislatorVoteFetchJob]] limits concurrency to 1 per bill (`key: ->(bill_id, **_kwargs) { "legislator_votes_#{bill_id}" }`) with `on_conflict: :discard`, preventing duplicate workers from competing over the same bill.
5. **Production verification and chamber isolation**: On the production path, [[app/jobs/legislator_vote_fetch_job.rb#LegislatorVoteFetchJob#run_service_for]] routes federal measures directly to [[app/services/congress_legislator_vote_update_service.rb#CongressLegislatorVoteUpdateService]]. The service scrapes each chamber independently. House roll calls use the official Congress.gov v3 REST endpoint with a fallback to `clerk.house.gov` XML; Senate roll calls query `senate.gov` XML with a fallback to Voteview JSON. Before persisting records, [[app/services/congress_legislator_vote_update_service.rb#CongressLegislatorVoteUpdateService#verify_record!]] confirms that the roll call occurred on the expected date ([[app/scraper/scraper/congress/roll_call_identity.rb#RollCallIdentity#taken_on?]]) and represents a position on the bill ([[app/services/congress_legislator_vote_update_service.rb#CongressLegislatorVoteUpdateService#verify_question!]]) rather than a procedural motion, enforcing the safety invariants in [[roll-call-identity]].
6. **Sponsor inference shield**: If a chamber's roll call is unfetchable (raising [[app/scraper/scraper/congress/roll_call_unavailable.rb#RollCallUnavailable]]) or fails validation, [[app/services/congress_legislator_vote_update_service.rb#CongressLegislatorVoteUpdateService#eligible_for_sponsor_inference?]] evaluates to `false`. Unfetchable roll calls never trigger sponsor inference, ensuring synthetic votes are never fabricated when an upstream source is unavailable. Valid votes for the opposing chamber are persisted, coverage is recorded, and the exception propagates for scheduled retry.
7. **Execution observability**: Cron health and execution durations are tracked via cron check-ins in Sentry as described in [[scheduled-job-monitoring]].

## Architectural path for sub-daily congressional timeliness

If sub-daily timeliness is needed, scheduled polling of official API endpoints or chamber XML feeds provides a reliable, outbound-only trigger.

When product requirements call for sub-hour vote discovery rather than the daily 09:00 UTC sweep, an outbound polling architecture satisfies timeliness goals without inbound email complexity:

- **Session-windowed polling**: Congressional floor voting follows predictable schedules, occurring primarily Tuesday through Thursday between 14:00 and 23:00 UTC. A lightweight recurring job scheduled during active legislative session windows provides timely discovery without 24/7 resource drain.
- **Direct chamber feed queries (unplanned option)**: An architectural alternative for sub-daily discovery is polling the recent-votes XML endpoint on `clerk.house.gov` or the vote listing on `senate.gov`. However, polling Clerk XML is not currently planned; Sway uses `clerk.house.gov` XML strictly as a secondary fallback stage during targeted bill vote fetching when Congress.gov has not yet ingested the roll call, rather than an unanchored discovery feed.
- **Official API integration**: Sway already maintains authenticated connection infrastructure for `https://api.congress.gov/v3` via [[lib/sway/faraday_stack.rb#FaradayStack#congress_gov]] and the `CONGRESS_GOV_API_KEY` credential (currently used for federal roster synchronization in [[app/services/legislation/adapters/generic_roster_adapter.rb#GenericRosterAdapter]]). The 5,000 request-per-hour quota easily accommodates periodic queries across active measures with negligible resource utilization.
- **Zero attack surface**: Outbound HTTPS requests require no open ports, no public mailboxes, no DKIM verification, and no credential management beyond existing API keys, preserving the stability and security of the edge deployment.
